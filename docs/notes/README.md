# Notes

Repo-wide decisions and their reasons. A part's own notes live beside this file, under `docs/notes/<group>/<part>/`: [skills/memory](skills/memory/README.md) is the first.

## Layout, 2026-10-15

- `packages/` holds what runs beside or inside AnythingLLM (bridge, mcp, skills). `app/` is the phone client and sits outside it. `contract/` is shared data, not a package.
- The Python parts form a uv workspace (one lock, shared ruff rules), and the JavaScript parts one `package.json` (one install); each part stays a separate distribution. Sharing tooling is allowed; sharing modules is not.
- Each skill ships as its own zip, so a skill is the package, and `packages/skills/` only groups them.
- No `.github/`. The gate is `lefthook.yml` calling the scripts in `tools/`, so the root gets one file and no hooks folder, and local and any later CI run the same scripts. The cost: nothing tests Windows or macOS (the mcp deploy's native mode, and the launchd and Task Scheduler managers the Python bridge had), a hook can be skipped with `--no-verify`, and there is no clean-room run. A hosted workflow can come back for the OS matrix alone.
- Parts are named by role. The bridge was `anythingllm-toolkit` and is now `anythingllm-bridge` (see the bridge section below).

## TypeScript under packages/skills, 2026-10-15

- **One config, at `packages/`** (first at `packages/skills/`): `tsconfig.json` beside `package.json`; the repository root has neither, because it is Python and Flutter. It includes every skill's `src` and tests and `shared/` by glob, so a new skill needs no config of its own.
- **`packages/shared/` holds helpers, and a part's output still stands alone.** A skill or the bridge imports `#shared/...`, which `package.json`'s `imports` field maps to `shared/*.mts`; Node, `tsc` and `esbuild` all resolve it, so tests, the type-check and the bundle use one mechanism (a `paths` alias would be invisible to Node). `esbuild` bundles the helper into the skill's `handler.js`, which then requires only Node built-ins; `tsc` alone would leave the import in the output. This relaxes the old rule "nothing a part ships imports from outside it": `shared/` is dependency-free source copied in at build, never a runtime import, so a fix in it reaches a part only when that part is rebuilt. First helper: `writeAtomic`, which was written separately in `apps`, `browser` and `memory`, and by hand in the bridge's `saveEnv`; it moved from `skills/shared/` to `packages/shared/` when the bridge became its second user, and `build.mjs` allows `shared/` for both parts.
- **Node 22.18+ to develop, Node 18 for the shipped code.** Node runs `.ts` itself (type stripping), so there is no `tsx`; `typescript`, `esbuild` and `@types/node@18` are the only dev dependencies, the last so that a newer API fails the type-check. Skills bundle with `--target=node18`, the bridge with `node20`. `erasableSyntaxOnly` keeps the source strippable (no enums); TypeScript 7 dropped `moduleResolution: node`, so the config uses `module: preserve` with `bundler`.
- **ESM is chosen by extension, not by a `package.json`.** `packages/package.json` has no `"type"`, so `.js` and `.ts` are CommonJS, which the skills need (AnythingLLM `require`s them, and the CommonJS fixtures and the built `handler.js` sit under it). Whatever is ESM is `.mts` (the shared helper, the tests, the bridge's source) or `.mjs` (`build.mjs`). A `"type": "module"` anywhere above a skill would break it; in a nested `package.json` it also turned the CommonJS fixtures into ESM. (Earlier there were nested `package.json` files for this; renaming to `.mts` removed them.)
- **Not done yet:** files a skill ships beyond `handler.js` and `plugin.json` need a place in `packages/build.mjs`.

## The bridge, rewritten in TypeScript, 2026-10-15

- **From `anythingllm-toolkit` (Python), keeping its behaviour on the wire:** the routes, the allowlist's rules, the `{"error": ...}` shapes and statuses, the 120 s timeout, the key check's cache (60 s good, 10 s refused), the login that is read afresh and retried after a 401. The layers (`cli`, `api`, `adapters`, `core`) and their `Protocol` ports became nine flat files, because a function argument is enough to put a fake in at that size.
- **Renamed to `bridge` throughout.** The command is `anythingllm-bridge`, the file `bridge.env` in `~/.config/anythingllm-bridge/`, the port `BRIDGE_PORT`, `/health` says `"service": "anythingllm-bridge"`. `TOOLKIT_DATA` and `TOOLKIT_SERVICE` went with the venv and the service managers. **Two names are not changed yet and are the app's and the MCP servers' to follow:** the pairing link's `toolkit=` field (AnywhereLLM Lite reads it by that name), and what `packages/mcp` reads (`ANYTHINGLLM_TOOLKIT_URL`, `~/.config/anythingllm-toolkit/toolkit.env`, the `toolkit_client` package). The bridge writes `ANYTHINGLLM_BRIDGE_URL` into the servers' env files, so the MCP servers do not find it until they are moved in and renamed to match. Change them together. *(Done for the MCP side: see "The control server" below. The pairing link's `toolkit=` field is still the app's.)*
- **One file, no dependencies:** `node:http`, `fetch` and `util.parseArgs` replace FastAPI, httpx and Typer. The artifact is `dist/anythingllm-bridge.cjs`, with the default allowlist from `contract/default-allow.txt` inlined by esbuild. It is `.cjs` so that a fixed extension makes the file run the same wherever it is copied (`.mjs` would do as well; nothing needs CommonJS here, unlike the skills, which AnythingLLM `require`s). The target is Node 20, the system's.
- **Left out on purpose:** the launchd and Windows Task Scheduler managers (never run on real hardware), the venv building (there is no Python), `--container` discovery through podman or docker (`install --storage` only), the QR code (`pair` prints the link), `routes`, `logs`, the migration from earlier default allowlists (nothing is installed to migrate). `health` keeps the checks that still apply.
- **Tests import `src/` directly** (Node strips the types) and run the real server against a fake AnythingLLM on a port of its own, so one test covers login, key check, allowlist, forwarding and error shapes together. `bundle.test.mts` runs the built file. Not covered: a real `systemctl` (`service.test.mts` scripts it) and a real AnythingLLM.
- **One `package.json`, one `tsconfig.json` and one `build.mjs` for the JavaScript parts, at `packages/`.** `package.json` holds the toolchain (`typescript`, `esbuild`, `@types/node`), the scripts (`typecheck`, `bridge:test`, `skills:test`) and the `#shared/*` imports map; `shared:test` runs the helper's tests and `build.test.mts` (the boundary check), and `tools/check` runs it before either part's tests; there is one `node_modules/` and one lock, and the repository root gained nothing. There are no npm workspaces: nothing a part ships has a dependency. There is no `package.json` in `bridge/` or `skills/`; module types follow the extension (see above). The type-check covers both parts in one run, so `tools/check bridge` also type-checks the skills and the reverse, and the bridge is checked against Node 18's types (`@types/node` is pinned for the skills; the bridge targets Node 20 and uses nothing newer). `packages/mcp` is Python and not part of it. `tools/boundaries` lost its two ast-grep rules, which compared two Python packages. What remains of the rule "no part imports another": `build.mjs` fails a bundle that took in a file from outside its part (the bridge's `src/`, `shared/` and the contract; a skill's `src/` and `shared/`), the app is grepped, and a Python part cannot import a TypeScript one. A type-only import or one in a test is erased or not bundled, so the build check does not see it; a grep rule like the app's would.

## Follow-ups to the bridge, 2026-10-15

- **The boundary check has a test** (`packages/build.test.mts`): a bundle that takes in a file outside its allowed prefixes fails and leaves no output, `clean` is what is removed, and a prefix is a folder (`a/src-old/` is not `a/src/`). `build.mjs` exports `bundle()` and runs the builds only as the entry script.
- **A client that leaves ends the upstream call.** The server aborts a controller when the response closes unfinished, and `Upstream.exchange` passes the signal to `fetch` (with the timeout, through `AbortSignal.any`, Node 20.3+). The shared login and key check get no signal, since other callers wait on them. An aborted call is an `AbortError`, not a 502, and is not retried; it is logged as `client closed`. A POST may already have taken effect upstream, as with any dropped connection.
- **`service.usable` asks the manager, not the machine:** `systemctl --user is-system-running` answering running, degraded or starting, through the injected `Run`. That made the start path testable (`service.test.mts`) and changed one behaviour: a host with systemd but no user session bus (ssh without lingering) now gets the "run `serve` under your own supervisor" hint instead of a failing `enable`. `uninstall` and `health` key on the unit file existing, not on the manager answering: `uninstall` tries `disable --now` whenever `install` defined a unit and says so when systemctl refuses. The bridge needs Node 20.3 for `AbortSignal.any` (the README and `build.mjs` say so; nothing checks it at start).
- **Still not run:** a real `systemctl` and a real AnythingLLM.

## The MCP package starts from a hello server, 2026-10-15

- **Built from nothing, not moved in.** `anythingllm-mcp`'s servers are still there. To see how lean the Python side can be, `packages/mcp` began with one server (`hello_mcp`, one tool) and what it takes to ship and check it: 3 source files (one empty), 1 test, 1 direct dependency (`mcp`). The old package needed `fastembed`, `httpx` and `numpy` as well, for servers that are not here.
- **One test, over stdio.** `tests/test_stdio.py` starts `python -m hello_mcp` with the SDK's own client, lists the tools and calls one. It covers the entry point, the transport and the tool together, so there is no separate unit test and no e2e script loop. It is a plain sync test around `asyncio.run`, so there is no `pytest-asyncio`.
- **`main` is folded into `__main__`.** The console script points at `hello_mcp.__main__:main`; the old servers had a `main.py` and a `__main__.py` that only called it.
- **Left out until they have something to do:** import-linter (needs two packages to layer), a `reported` wrapper around tools (needs a tool that raises), a bridge client and its settings (needs a server that calls the bridge), and registering a server in AnythingLLM's MCP servers file (`deploy_mcp` is not moving; the control server's own `install` does it, see the last section).
- **Ruff.** The part's `pyproject.toml` extends the root's rules and relaxes only what a test needs (asserts, annotations, literals). `uv run --locked ruff check` from the root, as the pre-commit hook runs it, works with no root dev group.
- **The chat server is next.** When it moves in, the rename that the bridge section above calls for happens with it: `ANYTHINGLLM_TOOLKIT_URL` to `ANYTHINGLLM_BRIDGE_URL`, and `toolkit_client` to a bridge client.

## A server that calls the bridge: world_mcp, 2026-10-15

- **One tool, `world_workspaces`, one route (`GET /workspaces`),** to test a server's calls to the bridge with the least code. `build_server` takes an `httpx.AsyncClient` already pointed at the bridge and carrying the key, so a test puts in a mock transport and `__main__` puts in the real one; there is no client class, port or settings type yet. `httpx` is now a direct dependency (the `mcp` SDK already pulled it in).
- **Three layers of test:** the mock-transport tests for the request and each refusal; a **contract test** that the route is in `contract/default-allow.txt`, using a small copy of the bridge's matching rules (`allow.mts`: no method means GET, POST, PUT or DELETE, whole segments, `*` for one) with its own test so it cannot pass vacuously; and a stdio test against a stand-in bridge over real HTTP. The copy of the matching rules is the price of Python not importing TypeScript; if `allow.mts` changes how a rule reads, `test_the_allow_check_would_catch_a_route_the_list_lacks` is the place to follow.
- **Errors:** the bridge's refusal is passed to the agent as it was said (`the bridge answered 403: the bridge doesn't pass ...`), and an unreachable bridge is said so. No error classes: one `ToolError` with a message.
- **Not tried:** the real bridge in front of a real AnythingLLM. The bridge's own tests run it against a fake AnythingLLM in Node; this part's tests stand in for the bridge.

## tools/e2e: the servers against a real AnythingLLM and the real bridge, 2026-10-15

- **What it starts:** a container of the pinned image on a free port (password and JWT secret passed as `-e`, no bind mount), the bridge built from `packages/bridge` on another with the default `BRIDGE_ALLOW`, a developer key made through the same login the settings page uses, and a workspace made with that key. It then runs `packages/mcp/e2e` with `E2E_BRIDGE_URL`, `E2E_DEVELOPER_KEY` and `E2E_WORKSPACE`. Run by hand first (the same steps), then scripted.
- **No bind mount, on purpose:** with a mounted storage folder, rootless podman leaves it owned by a sub-uid that the user cannot delete without `podman unshare`, and the bridge would not be able to read AnythingLLM's `.env`. The bridge gets the password from an `.env` of its own in the temporary folder (`ANYTHINGLLM_ENV`), which is also why nothing is kept: stopping the `--rm` container removes its storage.
- **Never touches what is running:** free ports, a container named for the script's pid, a settings file for the bridge (`BRIDGE_ENV_FILE`) and a `MCP_ENV_DIR` inside the temporary folder, so `~/.config` is not read or written. The trap kills the bridge by pid (an earlier `pkill -f` matched its own shell) and was checked on success, on a failing test and on SIGTERM.
- **Not a hook:** it needs a container engine and an image, so it is `make e2e` and not in `lefthook.yml` or `tools/check`. The first run pulls the image.
- **What it found:** nothing the mock-based tests had wrong on `GET /workspaces`; the bridge's 401 and 403 are as `contract/endpoints.md` and the bridge README say. One rough edge: a refusal reaches the agent with the bridge's raw `{"error": ...}` in it.
- **Not covered yet:** routes other than `GET /workspaces`. The chat and schedule routes in `default-allow.txt` come with the servers that call them. *(Done: see "The control server" below.)*

## The control server: chat and schedule as roles of one MCP server, 2026-10-15

- **Reverses an earlier layering.** `anythingllm-mcp` kept `chat_mcp` and `schedule_mcp` as two servers over a shared `toolkit_client`, with import-linter contracts so that neither read the other. They are now one server, `control_mcp`, with a role for each. What is kept is the separation that matters: a role the client did not ask for has no tools. *(Correction, same day: this note first said AnythingLLM can only switch a whole MCP server on or off, so the roles were the only per-client knob. That is wrong for 1.16.2, which can switch single tools off: `anythingllm.suppressedTools` in its servers file, and toggles on its MCP page. The roles still matter for clients without such a switch (Claude Desktop, an IDE) and because a tool that is not listed cannot be switched back on by mistake; the bridge's `BRIDGE_ALLOW` is global.)* **Only `chat` is on by default**, because a scheduled job runs a prompt as the agent, unattended: adding one is a way to plant an instruction that runs later.
- **Why merge:** the two shared a client, the env variables and the developer key, and repeated the same server skeleton and error wrapper. Together they had 11 tools and AnythingLLM's MCP page warns above 10. `schedule` is now one tool with an `action` (list, add, update, delete), as the sandbox's tools are, so both roles together are 8.
- **One error type.** `BridgeError` replaces six exception classes (`McpError`, `UnavailableError`, `UnauthorizedError`, `ToolkitRefusedError`, `NotFoundError`, `InvalidInputError`). Nothing caught them apart; each carried a message to the agent. The cost is in the tests: where one used to name the class it now names the message, and `test_chats.py` and `test_jobs.py` match on it. `ToolkitApi`, the Protocol with one implementer, is gone: `Chats` and `Jobs` take the `Bridge` client, and tests put a mock transport under it.
- **The bridge's `{"error": ...}` is unwrapped,** so the agent reads `403: the bridge doesn't pass GET /x`, not the JSON around it (the first real run showed the JSON).
- **`pytest-asyncio` is back,** with `asyncio_mode = "auto"`: the hello skeleton could do without it, about sixty async tests cannot.
- **Names changed with the move,** as the bridge section above said they must: `ANYTHINGLLM_TOOLKIT_URL` is `ANYTHINGLLM_BRIDGE_URL`, `toolkit_client` is `control_mcp.bridge`, and the bridge's `install` writes one `control.env` where it wrote `chat.env` and `schedule.env` (nothing is installed from before, so there is nothing to migrate). The bridge's tests were changed for it; they ran here only as far as `tsc` and the install tests compiled with esbuild on Node 20, since `tools/check bridge` needs Node 22.18 and npm, which this machine lacked.
- **Tests:** the unit tests run against a fake AnythingLLM under the real client. `test_contract.py` checks every route a tool calls against `contract/default-allow.txt`, with a copy of the bridge's matching rules that has a negative test of its own (removing the `DELETE /workspace/*` rule from the list makes it fail, which was tried). `tools/e2e` runs the same tools against a real AnythingLLM 1.16.2 and the built bridge. The old stand-in e2e scripts (about 190 lines) were not ported.
- **Left in `anythingllm-mcp`:** `memory_mcp` (not a control: its own SQLite store and embedding model, and the `memory` skill replaces it), `sandbox_mcp` (podman, an egress proxy, its own permission model) and `deploy_mcp` (an installer; the bridge's `install` and the control server's `install` replace it). The `hello` and `world` skeletons are gone; git has them.
- **Not tried:** a chat with real exchanges against the real AnythingLLM (the throwaway has no model); saved memories, workspace settings and the other native controls, which would be roles of this server.

## Installing the control server into AnythingLLM, from deploy_mcp's notes, 2026-10-15

- **Why it is needed:** nothing registered the control server with AnythingLLM. `deploy_mcp` (1,028 lines for four servers, two modes, a dry-run plan, a status command, a sandbox image build) did, and is not moving in. This is `anythingllm-mcp-control install | uninstall`, one module (`control_mcp/install.py`, about 260 lines with its docstrings and the two unit texts) and no new dependency.
- **Kept from deploy_mcp, because the problem is the same:** AnythingLLM runs in a container with no Python, so the server runs on the host, socket-activated by systemd (a socket unit and a service template, `Accept=yes`, stdin and stdout bound to the connection), and the container reaches the socket in its storage folder through a relay. A 0600 socket in the storage folder is better than the alternative AnythingLLM 1.16.2 does offer (an SSE or streamable HTTP server): from a pasta container the host's loopback is not reachable, so the server would have to listen on a routable address with the developer key behind it.
- **Changed, to cut bloat:**
  - the relay is a `node -e` one-liner inside the entry, so there is no `bridge.js` to ship, copy or find again (it was also easy to confuse with this repository's bridge);
  - the unit is `ExecStart=<the python that ran install> -m control_mcp`, so there is no wheel to build, no `uv tool install` and no folder of installed commands, and the units always run the checkout's code;
  - the unit texts are two f-strings, not template files with placeholders;
  - one server, so one name, `control`, for the entry, units, env file and socket, and no per-server loops;
  - no Host port and Action classes: the steps are done where they are written, and what the tests need replaced is one `Machine` dataclass (environment, home, the command runner, python);
  - no mode auto-detection by inspecting running containers: default is container where `systemctl --user` answers, else native, and `--native` says so outright;
  - no dry-run, status or secret masking: `install` prints what it did, and the README points at `systemctl --user status` and the servers file;
  - the storage defaults to the bridge's `ANYTHINGLLM_STORAGE`, so after `anythingllm-bridge install` it takes no arguments (deploy_mcp read the old toolkit's settings for this).
- **Ownership of an entry** is decided by what it starts (the socket path, or `control_mcp`): a `control` entry that is not ours stops `install` with a message, where deploy_mcp skipped it. The servers file is written in place, not by rename, because it belongs to AnythingLLM's user and group. A reinstall keeps the `anythingllm` block AnythingLLM keeps in our entry (`suppressedTools`, `autoStart`: set from its MCP page), since replacing the whole entry would have reset them. Marking our entries with a key of our own under `anythingllm` was not done: nothing shows that AnythingLLM keeps unknown keys there.
- **Tested:** the unit tests cover the texts, the merge and the idempotence with a recording `systemctl`. `tools/e2e` (podman) runs `install --no-start` into the storage of the throwaway container, started with `--userns=keep-id:uid=1000,gid=1000` so the container's user is the host user and the socket is reachable at 0600, with `systemd-socket-activate --accept --inetd` standing in for the two units, then makes AnythingLLM reload its MCP servers and lists `control` running with its tools. Removing the listener makes that test fail (tried). The real `systemctl enable --now` was **not** run: it would put units into the user's systemd.
- **Not carried over:** the sandbox image build, memory and sandbox themselves, Windows and macOS (the old command's native mode named `.exe` files; untested there too), and retiring the old `anythingllm-mcp-chat` and `-schedule` units, which the README says how to do with the old command.
